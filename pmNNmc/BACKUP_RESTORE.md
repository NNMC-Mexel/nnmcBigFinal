# Резервное копирование и восстановление

Закрывает §21.3 ТЗ (RPO 24 ч, RTO 4 ч для критичных модулей).

> Статус на 2026-08-07: **бэкапов нет**. Это единственный класс проблем в проекте,
> который нельзя исправить постфактум — всё остальное лечится откатом.
> Пока этот документ не выполнен, любая правка прода делается на свой страх.

## 1. Что бэкапим

| # | База | Приложение в Coolify | Что потеряем без неё |
|---|---|---|---|
| 1 | `nnmc_board` | server-pm (core) | Проекты, задачи, HelpDesk, новости, протоколы, уведомления, аудит |
| 2 | `nnmc_bpm` | server-bpm | BPM-заявки, онбординг, АРТ-табель, карточки сотрудников |
| 3 | KPI | server-kpi | KPI, табели, архивы расчётов, справочник 1С |
| 4 | `conference_rooms` | server-conference | Брони переговорных |
| 5 | Журнал приемной | server-priemnaya | Входящая/исходящая корреспонденция |
| 6 | SignDoc | server-sign-doc | Реестр документов и подписей ЭЦП |
| 7 | **База Keycloak** | keycloak | **Все учётные записи.** Без неё в систему не войдёт никто |

Строка 7 — самая важная и про неё чаще всего забывают. Бэкап БД Keycloak надёжнее
JSON-экспорта realm: экспорт по умолчанию не содержит учётных данных пользователей.

Отдельно от БД: **MinIO** (`192.168.101.25:9000`) хранит загруженные файлы, сканы
документов онбординга и подписанные PDF. Дамп БД без MinIO восстановит записи
с битыми ссылками на файлы.

## 2. Настройка в Coolify

Для каждой из 7 баз:

1. Coolify → Project → выбрать ресурс базы данных → вкладка **Backups**.
2. **Add backup**:
   - Frequency: `0 3 * * *` (ежедневно в 03:00, вне рабочих часов).
   - Retention: 30 дней.
   - Destination: S3.
3. Сохранить, затем **Run backup now** — не ждать ночи, убедиться сразу, что задание
   отрабатывает и файл появляется.

Если вкладки **Backups** у ресурса нет — эта база развёрнута не как Coolify-ресурс,
а как сервис внутри docker-compose. Тогда либо перенести её в отдельный ресурс,
либо использовать вариант из раздела 5.

### Куда складывать

В MinIO на `192.168.101.25:9000` уже есть S3-совместимое хранилище, и это
самый быстрый вариант настройки. **Но он не годится как единственный:** MinIO
живёт на том же хосте, что и базы. Отказ диска или хоста уносит и данные, и бэкапы.

Минимально приемлемо: MinIO как основная копия **плюс** еженедельная выгрузка
за пределы хоста (другой сервер, NAS, внешний S3). Требование §21.3 «хранение
копий по политике Заказчика» без второй площадки не выполняется.

## 3. Проверка восстановления — обязательна

Бэкап, который ни разу не разворачивали, бэкапом не является. Один раз при
настройке и далее ежеквартально:

```bash
# на хосте Coolify
docker exec -i <postgres-container> \
  createdb -U <user> restore_test

docker exec -i <postgres-container> \
  pg_restore -U <user> -d restore_test --no-owner < <файл-бэкапа>

# проверить, что таблицы на месте и не пустые
docker exec -i <postgres-container> psql -U <user> -d restore_test -c '\dt' | head -20
docker exec -i <postgres-container> psql -U <user> -d restore_test \
  -c 'select count(*) from up_users;'

# убрать за собой
docker exec -i <postgres-container> dropdb -U <user> restore_test
```

Восстанавливать **в новую базу** `restore_test`, никогда не поверх рабочей.

Зафиксировать результат: дата проверки, размер дампа, время восстановления.
Последняя цифра — и есть фактический RTO, а не заявленные 4 часа.

## 4. Перед рискованным деплоем

Ночного бэкапа недостаточно, когда деплой трогает `bootstrap()` или схемы
content-type: откат кода не откатывает миграции БД.

Порядок: **Run backup now** → дождаться завершения → деплоить.

Относится к изменениям в `src/index.ts` любого сервиса, любым правкам
`content-types/*/schema.json` и апгрейдам версии Strapi.

## 5. Запасной вариант: если Coolify не управляет базой

```bash
#!/usr/bin/env bash
# /opt/nnmc-backup.sh — вешается в cron: 0 3 * * *
set -euo pipefail

CONTAINER="<имя-postgres-контейнера>"
PGUSER="<пользователь>"
DEST="/opt/backups/nnmc"
KEEP_DAYS=30
STAMP="$(date +%Y%m%d-%H%M%S)"

mkdir -p "$DEST"

# pg_dumpall забирает все базы разом вместе с ролями — не нужно
# перечислять базы и хранить отдельные пароли.
docker exec "$CONTAINER" pg_dumpall -U "$PGUSER" \
  | gzip > "$DEST/all-$STAMP.sql.gz"

# Пустой или обрезанный дамп хуже отсутствующего: он создаёт ложное
# ощущение защищённости. Проверяем до ротации.
if [ ! -s "$DEST/all-$STAMP.sql.gz" ] || ! gzip -t "$DEST/all-$STAMP.sql.gz"; then
  echo "БЭКАП ПОВРЕЖДЁН: $DEST/all-$STAMP.sql.gz" >&2
  exit 1
fi

# Ротация только после успешной проверки свежего дампа.
find "$DEST" -name 'all-*.sql.gz' -mtime "+$KEEP_DAYS" -delete

echo "OK: $DEST/all-$STAMP.sql.gz ($(du -h "$DEST/all-$STAMP.sql.gz" | cut -f1))"
```

Порядок в скрипте важен: сначала проверка целостности, потом удаление старых.
Обратный порядок при сломанном `pg_dumpall` за 30 дней вычистит все копии.

## 6. Чего этот документ не покрывает

- **Мониторинг результата.** Молча упавший cron неотличим от работающего.
  Нужен алерт на отсутствие свежего файла.
- **Восстановление MinIO** — версионирование либо репликация бакета.
- **Проверка на staging.** Ветка `staging` отстаёт от `main` на 127 коммитов
  (последний коммит 2026-06-04) и полноценным полигоном сейчас не является.
